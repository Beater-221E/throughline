# Throughline 技术报告

> 工作流程、组件选择依据与实验数据。所有数字都来自作者本机的真实会话语料与可复现的评测脚本；
> 口径与局限在第六节和附录中明确标注。

## 1. 摘要

Throughline 解决一个具体问题：**当你要继续一件跨会话的工作时，agent 不记得之前说过什么。**

我们的答案是「检索」而不是「沉淀」：把历史会话按对话轮次建成本地索引，暴露一个 `memory_search`
工具让 agent 按需召回。索引由三部分组成：SQLite FTS5（中文用字符 bigram 的词法通道）、
一个多语 int8 向量模型（`multilingual-e5-small`）、以及一个简单的混合排序（默认 0.7 向量 + 0.3 词法，可调）。
全部本地运行，单次检索约 1–5 ms，1,312 轮语料的索引体积约 10 MiB。

在 1,312 turn / 58 会话的真实中英混合语料上，75 条分层查询的总体 nDCG@10 为 **0.310**（默认 0.7 稠密）、
MRR 0.491、R@5 0.627；把稠密权重降到 0.3（词法偏重）时为 0.275。分层看：锚点查询 0.55，改写查询 0.31，
跨语言查询 0.07——最后一项是已知短板，且是模型能力限制而非排序问题。

## 2. 问题与边界

### 2.1 要解决的问题

在长期使用 agent 的过程中，大量信息只在会话里出现过一次：某个脚本的名字、某次实验的结论、
某个约定的交付标准。下一个会话开始时，这些信息不在上下文里。用户的典型反应是「我上次说过」，
或者重新解释一遍。

### 2.2 为什么不做「自动沉淀成 AGENTS.md」

这是本项目早期的另一条路线，我们在 24 个会话片段上做过测量，结论是**写侧的成本高于收益**：

| 测量 | 结果 | 含义 |
|---|---|---|
| 继续任务时探索性 token 的重复率 | 28.8% | 看起来有优化空间 |
| 其中真正与「记忆内容」相关的重复 | 10.8% | 其余是环境重建 |
| 重复 token 中环境重建（重跑 shell、重看目录）的占比 | **89%** | 大头属于持久化 shell 问题，不是记忆问题 |
| 错误签名在后续会话中复现的比例 | **12.2%**（即 87.8% 不复现） | 错误记忆的价值很低 |
| 蒸馏出的知识页体积 | 与语料同量级 | 压缩比接近 1，写侧没有净收益 |

此外，自动维护 `AGENTS.md` 还引入三类风险：规则写入错误会持续影响后续会话；规则与代码演进不同步；
以及「谁有权改这条规则」的治理问题。因此我们选择只做读侧：**索引原文，按需检索，不产生派生知识**。

### 2.3 非目标

- 不做记忆浏览器/编辑器（索引是派生物，可随时重建）。
- 不做云端同步、多租户、鉴权（本地单用户工具，路由只监听 localhost）。
- 不自动改写你的会话日志（只读）。

## 3. 系统工作流

```
┌──────────────────────────── DSH ────────────────────────────┐
│  agent/created 事件                                          │
│       │                                                      │
│       ▼                                                      │
│  Host 插件 index.js ──► 触发一次增量入库（去抖 60s，单写者锁） │
│       │                                                      │
│       ▼                                                      │
│  ingest.mjs：逐帧解压 session.v4.jsonl.zstd                   │
│       │  提取 user 消息 + assistant 文本块                    │
│       │  丢弃注入上下文 / 工具调用 / 工具结果 / 推理          │
│       │  排除规则（工作区/会话/关键词）+ 凭据脱敏              │
│       ▼                                                      │
│  memory.py add：SQLite turns + FTS5 + 向量桶                  │
└──────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴────────────────┐
              ▼                                ▼
     memory_search 工具                 设置页 / 路由
     （模型主动调用）                    （状态、暂停、重建、排除）
```

### 3.1 触发模型

| 触发 | 行为 | 目的 |
|---|---|---|
| 插件首次加载且索引为空 | 后台全量入库 | 无需手动初始化 |
| 每个 `agent/created` | 扫描会话目录，只处理水位线之后变化的文件 | 增量、低开销 |
| 手动「重建索引」 | 清空后全量 | 模型/规则变化后重建 |
| 失败两次 | 30 分钟内不再触发 | 避免反复失败拖慢会话 |

关键约束：**当前活动会话不入库**（通过 `--exclude` 传入当前 session id，且要求文件最后修改时间
早于 120 秒）。这样避免了边写边读的不一致，也避免 agent 检索到自己正在生成的半截内容。

### 3.2 为什么是轮级（turn）而不是会话级

会话级的块太大：一个会话通常有 10–50k token，而一次提问真正需要的往往只是一两轮。
我们在早期实验里验证过：把命中轮次前后各扩 1–2 轮（共 3–5 轮）就能覆盖答案，
5 轮上下文的 payload 约 3k token，而整段会话是它的 5–10 倍。
轮级索引 + 预算装配的代价是「可能只召回半段论证」，收益是召回精度与 token 成本。

### 3.3 增量入库

每处理完一个会话，把 `(mtime, size)` 写进 `watermark.json`；下次只处理变化的文件。
按会话替换：入库前先删除该会话的旧行与词法行，再插入新行，因此修改提取规则或脱敏规则后
重新入库不会留下旧副本。

## 4. 组件选择与依据

### 4.1 存储：SQLite FTS5 + 自建向量桶

| 候选 | 否决/采纳理由 |
|---|---|
| 纯向量库（FAISS/Chroma） | 中文专名、命令、标识符的精确匹配差；本项目语料里这类查询占比高 |
| 纯词法（FTS5） | 改写查询全线失效（实测改写层 nDCG 仅 0.17 的稠密通道能救回一部分） |
| Elasticsearch | 对单用户本地工具过重（JVM、内存、运维） |
| 远程向量服务 | 违背「不联网」的前提 |
| **SQLite + numpy 桶** | 零依赖、单文件、事务与 FTS5 内置；向量用 int8 桶追加写 |

向量按桶追加（每桶 2048 条，`npz` 格式），避免每次增量都重写整个矩阵。删除行会产生孤儿向量，
因此在有删除时做一次压缩（重写桶），把体积拉回与行数匹配。

### 4.2 中文词法通道：字符 bigram

FTS5 默认分词器把一整段连续汉字当作一个 token，导致中文查询几乎无法命中。
我们改为在索引与查询两侧生成同一种词流：

- 拉丁词：`[a-zA-Z0-9_]+`，小写；
- 每个连续汉字段：字符 bigram + unigram。

这是全项目最大的单点收益。在 1,312 turn 语料上，纯词法的 nDCG 为 0.252，纯向量为 0.258，
而两者融合后默认（稠密 0.7）0.310、词法偏重（0.3）0.275——词法通道提供了向量无法覆盖的精确匹配，
向量通道提供了词法无法覆盖的改写召回。

### 4.3 向量模型：multilingual-e5-small

| 模型 | 体积 | 锚点 | 改写 | 跨语言 | 总体 nDCG | MRR |
|---|---|---|---|---|---|---|
| bge-small-en-v1.5 | 34 MB | 0.471 | 0.377 | 0.084 | 0.311 | 0.474 |
| bge-small-zh-v1.5 | 23 MB | 0.405 | 0.331 | 0.080 | 0.272 | 0.408 |
| **multilingual-e5-small** | **129 MiB** | 0.437 | 0.379 | 0.084 | 0.300 | 0.449 |

（快照 A：1,167 turn / 72 查询，混合排序。）

只看稠密通道，差异更清楚：e5 在改写层达到 0.168，而英文模型是 0.000（它无法编码中文）；
跨语言稠密召回上，e5 是 0.075，更大的 bge-m3（543 MB int8）是 0.195。我们选择 e5 的理由：

1. 中英混合是真实语料的主形态（972 中文 / 195 英文 turn），单语模型会直接丢失一半内容；
2. 129 MiB 是「可接受安装成本」的上限（onnxruntime 52 MB + tokenizers 8 MB，整体约 189 MB）；
3. 更大模型（bge-m3）在混合排序的总分上收益有限，却把安装体积推到 700 MB 以上。

模型通过 `service/model/model.json` 声明约定（pooling、query/passage 前缀、最大长度），
换模型只需改这个文件并重建索引。

### 4.4 融合权重：没有全局最优

在当前 1,312 turn / 75 查询的语料上重跑权重扫描（同一批查询、同一批金标）：

| 稠密权重 | 总体 nDCG | MRR | R@5 | 锚点 | 改写 | 跨语言 |
|---|---|---|---|---|---|---|
| 1.0（纯向量） | 0.258 | 0.409 | 0.520 | 0.485 | 0.172 | 0.117 |
| **0.7（默认）** | **0.310** | **0.491** | **0.627** | 0.547 | 0.312 | 0.072 |
| 0.5 | 0.292 | 0.472 | 0.560 | 0.461 | 0.345 | 0.071 |
| 0.3 | 0.275 | 0.448 | 0.533 | 0.391 | 0.356 | 0.080 |
| 0.1 | 0.257 | 0.422 | 0.507 | 0.328 | 0.363 | 0.081 |
| 0.0（纯词法） | 0.252 | 0.420 | 0.507 | 0.313 | 0.362 | 0.080 |

结论：**权重是语料与查询分布的属性，不是常数。** 稠密偏重（0.7）在锚点与总体指标上更好；
词法偏重（0.3）在改写层更好。在 1,167 turn 的早期快照上 0.3 曾是最优，语料增长到 1,312 后
最优点移到了 0.7——这说明它需要可调而不是写死。因此提供环境变量
`THROUGHLINE_DENSE_WEIGHT`（默认 0.7），部署方可以用自己的查询日志重跑扫描后再定。

### 4.5 为什么是 onnxruntime 而不是 PyTorch

- PyTorch 运行时约 2 GB，onnxruntime 约 52 MB；
- 语料规模（万级轮次）用 CPU int8 推理足够：1,312 条向量全量重建约 25 秒；
- 量化模型（118 MB）与 float32 相比在评测中无可见差异。

### 4.6 注入效率：摘录、去重、预算

检索返回的不是固定 top-k，而是一个按 token 预算装配的集合（默认 1500）。三项设计都只降低注入量、
不改变召回集合：

| 机制 | 作用 |
|---|---|
| **摘录模式** | 长轮次只保留命中句前后各一句（±1 句，最多约 600 字），短轮次原样返回 |
| **MMR 去重** | 同一决定常被多个会话重复引用；贪心选择时惩罚与已选轮次的词面重合（λ=0.35） |
| **预算收紧** | 3000 → 1500，让模型在需要时二次检索，而不是一次灌满 |
| **条数上限** | 最多 12 条，避免几十个短片段把上下文切碎 |

理由是：不同轮次的长度差异很大（几十到上千 token），固定 k 会让短查询拿到过多噪声、长查询拿到
过少上下文。摘录与去重针对的是「预算被重复内容和无关段落浪费」。预期把单次注入 token 降低
40–60%，但这个数字需要用任务级 A/B 验证（见 `VALIDATION.md`），不能只看注入量本身。
实测排序+装配耗时约 25 ms（1,312 turn），其中摘录与 MMR 占大头，embedding 只有约 2 ms。

### 4.7 人工层：pinned 与 glossary

自动检索无法保证「某条规则永远优先」，也没有离线词典能覆盖作者自造的中英术语。因此提供两个
纯文本的人工层：

| 层 | 机制 | 实测 |
|---|---|---|
| `pinned.md` | 每行一条规则；会话开始时**直接注入系统提示**（确定性生效），同时入库为 `session_id=pinned`、排序 +0.8 | 6 条定向查询 hit@3 从 4/6 提升到 **6/6**，中位名次 1 |
| `glossary.json` | 中文术语 → 英文/同义词，只扩展词法查询 | 24 条词表使总体 nDCG 0.300→0.367、改写层 0.379→0.580 |

诚实说明：词表是按评测主题编写的，因此 0.367 是**上界**。我们同时试过从语料共现自动挖掘词表，
结果把锚点层从 0.437 打到 0.156（噪声词污染查询），所以没有采用自动方案。

### 4.8 被否决的方案

| 方案 | 结果 | 结论 |
|---|---|---|
| 短轮次阻尼（cos × len/40） | −0.012，95% CI [−0.029, +0.002] | 伤害锚点查询，拒绝 |
| 自适应权重（词法命中少时切稠密） | −0.001 | 无效，拒绝 |
| 中文停用 bigram | 0.000 | 无差别，拒绝 |
| 510 token 窗口 | 0.000（长金标 R@10 39/72 不变） | 无收益，拒绝 |
| 语料共现自动词表 | 总体 0.203 | 噪声，拒绝 |
| 交叉编码器重排（bge-reranker-base int8） | R@1 0.347→0.417，R@5 0.528→0.611，MRR 0.449→0.506 | 质量有效，但 20 对/查询约 1.8 秒，超出延迟预算；保留为未来可选「深度检索」 |
| 日期过滤 | 6 条带日期查询 hit@5 1/6→2/6，名次 20→10、14→2、986→28 | 机制有效但证据弱（仅 4 条有同日金标），暂缓 |

## 5. 工程实现要点

### 5.1 一致性

- **单写者**：`ingest.lock` 带 pid 校验，加上 60 秒去抖，避免并发入库。
- **按会话替换**：删除旧行 → 插入新行，避免规则变化后残留旧副本。
- **崩溃修复**：`serve` 启动时检查 `vec_ok=0` 的行并补算向量（幂等）。
- **桶压缩**：有删除时重写桶，避免孤儿向量长期累积（实测修复前桶数会从 1 涨到 2、体积翻倍）。

### 5.2 服务生命周期

- 60 秒一次 `ping`；5 秒无响应杀进程重启，最多每分钟一次，状态暴露在设置页。
- 日志超过 1 MB 轮转；运行历史保留最近 50 次；事件日志保留最近 300 条。
- 设置页显示磁盘版本与已加载版本，不一致时提示重启。

### 5.3 成本

| 指标 | 实测 |
|---|---|
| 安装增量（依赖 + 模型） | 约 189 MiB |
| 索引体积（1,312 turn） | SQLite 8.2 MB + 向量 2.0 MB |
| 全量重建 | 26–28 秒（1,312 turn，CPU） |
| 单会话增量 | 约 3 秒 |
| 端到端检索 | 约 4.7 ms（含 FTS5 与向量打分，1,167 turn 时） |
| 纯排序耗时 | 1.2 ms（1,312 turn） |

### 5.4 隐私

- 只入库对话文本；工具调用、工具结果、推理内容一律丢弃。
- 凭据在入库前脱敏（`service/redaction.json`，JS 与 Python 共用同一份规则）。
  早期版本的正则会误伤 `token: 3,000字符` 这类正常文本；收紧为「要求密钥形状 + 词边界」后，
  在 1,167 turn 的语料上误报为 0。
- 支持按工作区/会话/关键词排除；排除只影响未来入库，历史内容在「重建索引」后消失。
- 索引可一键清空，会话日志永远只读。

## 6. 评测方法

### 6.1 协议

- 语料：作者本机的真实 DSH 会话，中英混合。
- 查询：24 个主题 × 3 个层次 = 72 条（当前快照 75 条，主题随语料增长略有增减）。
  - **锚点**：查询包含一个稀有 token（命令、模型名、标识符）；
  - **改写**：中文改写，与原文字面重合很少；
  - **跨语言**：中文内容的英文改写。
- 金标：包含该主题稀有 token 的轮次（每题 2–80 条）。
- 指标：nDCG@10（主）、MRR、R@5、R@1。
- 对照：同一批查询、同一语料、只改一个变量。

### 6.2 主结果（当前快照：1,312 turn / 58 会话 / 75 查询）

| 配置 | 总体 nDCG | MRR | R@5 | R@1 |
|---|---|---|---|---|
| 纯向量 | 0.258 | 0.409 | 0.520 | 0.293 |
| 纯词法 | 0.252 | 0.420 | 0.507 | 0.333 |
| **默认 0.7** | **0.310** | **0.491** | **0.627** | **0.387** |
| 0.3 | 0.275 | 0.448 | 0.533 | 0.360 |

分层（默认 0.7 / 0.3）：锚点 0.547 / 0.391，改写 0.312 / 0.356，跨语言 0.072 / 0.080。
锚点与改写之间存在明确的取舍：没有任何一个权重能同时最优。

### 6.3 可信度

- 72–75 条查询覆盖 24–25 个主题，同一主题的三条查询高度相关，因此**低于约 0.02 的差异不可分辨**；
  干预实验使用配对 bootstrap（1000 次）给出 95% 区间。
- 查询集偏锚点，这对词法通道有利；改写层是最诚实的弱项。
- 评测语料是作者个人会话，主题分布不代表通用场景；换语料需要重跑，不能直接引用这些数字。
- 权重扫描显示最优点随语料规模移动，说明这些数字是「该快照的属性」，不是模型的固有性质。

## 7. 局限与未来

| 局限 | 现状 | 可能的改进 |
|---|---|---|
| 跨语言召回弱 | 0.07–0.08 nDCG，模型能力限制 | 换更大模型（体积代价）或查询时翻译扩展 |
| 改写查询不稳定 | 0.31–0.36 | 人工词表（已支持）、更强的稠密模型 |
| 没有真实召回率 | 运行时只有命中率代理 | 离线评测是唯一可靠手段 |
| 单机单用户 | 路由无鉴权，仅 localhost | 明确不支持多用户 |
| 长轮次切分 | 510 token 窗口无收益，暂不切分 | 需要长回复专项评测 |
